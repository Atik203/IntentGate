## 1. Executive Summary / Core Claim

CaMeL (CApabilities for MachinE Learning) is a **system-level defense** that creates a protective layer around an LLM agent so that untrusted data **cannot** alter the agent’s control flow or exfiltrate private data over unauthorized data flows — even when the underlying model remains vulnerable to prompt injection.

**Key mechanism**:
1. A **Privileged LLM (P-LLM)** sees *only* the trusted user query and converts it into restricted Python code that expresses the intended control + data flow.
2. A **Quarantined LLM (Q-LLM)** processes untrusted tool outputs / documents but has **no tool-calling ability**.
3. A **custom Python interpreter** executes the plan while maintaining a data-flow / dependency graph and attaching **capabilities** (provenance + allowed readers) to every value.
4. Before any tool executes, **security policies** (expressed as ordinary Python functions) inspect the capabilities of the arguments and either allow, deny, or escalate to the user.

**Headline result on AgentDojo**:
- Solves **77%** of tasks with *provable security* (vs ~84% utility of an undefended native tool-calling system).
- In security evaluations with policies, attack success is driven essentially to zero for classic prompt-injection goals (with a few residual non-goals such as pure phishing text that never reaches a tool).

CaMeL requires **no fine-tuning or modification of the underlying LLM**. Security is architectural.

## 2. Problem Statement & Motivation

LLM agents that call tools (email, calendar, cloud storage, banking, web, etc.) treat tool returns as trusted observations. An adversary who can influence any of those returns can inject instructions that:
- Change which tools are called (control-flow hijack), or
- Change the *arguments* to otherwise legitimate tools (data-flow hijack → e.g. send a confidential document to the attacker).

Existing defenses (delimiters, prompt sandwiching, RLHF / instruction hierarchy, adversarial training) are heuristic and regularly broken. The **Dual LLM pattern** (Willison 2023) isolates planning from untrusted data but still leaves the data-flow channel open: the Quarantined LLM can be tricked into returning attacker-chosen values that are then fed into the planned tools.

CaMeL closes both channels by making the plan explicit code and enforcing fine-grained capability policies on every value that reaches a tool.

---

## 3. Threat Model

**Primary goal of CaMeL**: stop prompt-injection attacks that originate from untrusted data sources (emails, documents, web pages, tool outputs, shared files, etc.).

**Assumptions**:
- The user prompt itself is trusted.
- The user is not pasting untrusted text into the prompt.
- Persistent memory (if present) has not already been compromised.

**Adversary capabilities**:
- Can craft arbitrary content that the agent may later retrieve via tools.
- Can influence the *arguments* that reach tools even when the high-level plan is fixed.

**Explicit non-goals** (Section 3.1):
- Pure text-to-text attacks that never affect control or data flow to tools (e.g., rewriting a summary to be misleading, or classic phishing text that is only shown to the user).  
  → CaMeL’s data-flow graph can still be used by a UI to *highlight* untrusted provenance of displayed text.
- Fully autonomous operation with zero user interaction. Ambiguous queries or policy violations may still require user confirmation; the design aims to minimize unnecessary prompts and reduce security fatigue.

---

## 4. Formal Security Game (PI-SEC)

The paper formalizes the threat as the game **PI-SEC** (Figure 3):

- Adversary \(\mathcal{A}\) supplies an initial adversarial memory state `mem*`.
- Agent executes a trusted user `prompt` using the tools and returns a `Trace` of (tool, args, memstep) tuples.
- For each prompt there is a set \(\Omega_{\text{prompt}}\) of *allowed* actions.
- Adversary wins if the Trace contains any action outside \(\Omega_{\text{prompt}}\).

CaMeL is designed so that, under the enforced policies, the adversary cannot win this game for the class of attacks that affect control or data flow to tools.

## 5. Architecture Design

### 5.1 High-Level System Context

```
┌──────────────┐   trusted user query   ┌─────────────────────────────┐
│     User     │ ─────────────────────► │      Privileged LLM (P-LLM) │
└──────┬───────┘                        │  (generates restricted      │
       │ confirmation                   │   Python plan + schemas)    │
       │                                └──────────────┬──────────────┘
       │                                               │ code plan
       ▼                                               ▼
┌──────────────────────────────────────────────────────────────────────┐
│                        CaMeL Interpreter                             │
│  • builds / maintains data-flow & capability graph                   │
│  • invokes Q-LLM for structured extraction from untrusted data       │
│  • checks security policies before every tool call                   │
│  • either executes tool, blocks, or escalates to user                │
└───────┬───────────────────────────────┬──────────────────────────────┘
        │                               │
        ▼                               ▼
┌───────────────┐               ┌──────────────────┐
│ Quarantined   │               │  External Tools  │
│ LLM (Q-LLM)   │               │ (email, drive,   │
│ no tool access│               │  calendar, bank…)│
└───────────────┘               └──────────────────┘
```

### 5.2 Core Components

| Component | Role |
|-----------|------|
| **Privileged LLM (P-LLM)** | Sees *only* the user query + tool signatures. Emits restricted Python code that expresses the intended plan. Never sees raw tool outputs or Q-LLM answers. |
| **Quarantined LLM (Q-LLM)** | Parses untrusted unstructured data into a *structured* schema supplied by the P-LLM. Has **zero** tool-calling ability. Can only signal “not enough information” via a boolean field. |
| **Tools** | Ordinary agent tools (send_email, create_calendar_event, read_file, send_money, …). Each tool can attach capability metadata to its return values. |
| **Capabilities** | Metadata on every value: provenance (User / CaMeL / tool + inner source) and allowed readers (Public or set of identities, e.g. email addresses). |
| **Security Policies** | Ordinary Python functions `policy(tool_name, kwargs) → Allowed | Denied(reason)`. Inspect capabilities of arguments (and their full dependency graphs). Can be global or per-tool; designed to be extensible to user- or provider-supplied policies. |
| **CaMeL Interpreter** | Custom restricted-Python interpreter. Tracks dependencies, propagates capabilities, enforces policies, handles errors by re-prompting the P-LLM (with redaction of untrusted exception content). |

### 5.3 Execution Flow (Figure 5)

1. User submits natural-language query.
2. P-LLM emits Python code that calls tools and the Q-LLM (presented to the P-LLM simply as another callable).
3. Interpreter executes the code step by step:
   - Builds a data-flow / dependency graph for every value.
   - When a tool is about to be called, evaluates the relevant security policies against the arguments and their full dependency closure.
   - If policy returns `Denied` → block (or, in production, escalate to user).
   - If allowed → execute tool; tool may attach new capabilities to the returned value.
4. Q-LLM is invoked only for structured extraction; its output is treated as untrusted and inherits appropriate capabilities.
5. Side-effecting operations that survive policy checks may still require explicit user confirmation in a real deployment.

### 5.4 Capabilities in Detail

Each value carries:
- **Provenance / sources**: User (literals in P-LLM code), CaMeL (results of interpreter transformations), or a concrete tool (plus optional *inner source*, e.g. the sender of an email).
- **Allowed readers**: `Public` or a set of principals (typically email addresses).

Tools themselves can annotate returned values (e.g., a cloud-storage tool tags a document with its editors and the identities that already have read access).

Capabilities enable *fine-grained* decisions that pure control-flow or pure data-flow restrictions cannot express cleanly (example: a restaurant-booking tool may receive a phone number but must never receive a passport number).

### 5.5 Security Policies

Policies are ordinary Python functions. Example (calendar event creation):

```python
def create_calendar_event_policy(tool_name, kwargs):
    participants = kwargs["participants"]
    if is_trusted(participants):
        return Allowed()
    # Otherwise every piece of event data must be readable by the participants
    if not can_readers_read_value(set(participants.raw), kwargs["title"]):
        return Denied("The title is not public or shared with the recipients")
    # … same checks for description, location, times …
    return Allowed()
```

Policies can be as expressive as needed; the paper releases the full set used for AgentDojo with the code.

### 5.6 Interpreter Details

- Restricted Python dialect (no arbitrary imports, limited control structures, etc.).
- Two dependency modes:
  - **NORMAL**: dependencies follow ordinary data flow.
  - **STRICT**: control-flow conditions (if-tests, loop iterables) are also added as dependencies of variables assigned inside the block (prevents certain side-channel / conditional-exfiltration patterns).
- Error handling: up to 10 re-prompts of the P-LLM with exception type + location; exception *content* that depends on untrusted data is redacted.
- No atomicity / rollback for sequences that partially succeed and then fail (current limitation).

## 6. Evaluation (AgentDojo)

### 6.1 Utility

- Benchmark suites: Workspace, Banking, Travel, Slack.
- Models evaluated: Gemini 2.5 Flash/Pro, Claude 3.5 Haiku / Sonnet 4 (with & without reasoning), GPT-4.1, o4-mini (high), o3 (high), etc.
- **Result**: CaMeL retains the large majority of native-tool-calling utility. Typical degradation is small; on some model/suite combinations utility even *improves*. Travel suite is the main exception for older models (under-documented tool output schemas); newer models largely recover by using the Q-LLM to parse unknown structures.
- Cheaper / weaker Q-LLM (e.g. Claude 3.5 Haiku under Claude 4 Sonnet P-LLM) costs only ~1% utility while reducing median-task cost by ~12%.

**Main utility failure modes observed** (Claude analysis):
- “Data requires action” – the plan itself depends on untrusted data that the P-LLM is not allowed to see.
- Insufficient context passed to Q-LLM.
- Under-documented tool return schemas.
- Occasional over-eager Q-LLM transformations or ambiguous tasks.

### 6.2 Security

- **Without extra policies** (pure Dual-LLM isolation): already eliminates a large fraction of attacks because the plan cannot be rewritten by untrusted data.
- **With capability policies**: attack success rate for the classic AgentDojo injection goals is driven essentially to zero (or to the residual non-goals such as pure phishing text that never reaches a tool).
- Residual successful “attacks” are typically *not* prompt injections that change tool arguments; they are cases outside CaMeL’s stated goals (e.g., text that is only displayed to the user).

**Policy trigger frequency**:
- Workspace suite: relatively few denials (rich, accurate capability annotations available).
- Slack / Banking: higher denial rates (weaker identity information or very strict policies such as `send_money`).

## 7. Comparison with Related Defenses (especially CLAWGUARD)

| Aspect | CaMeL | CLAWGUARD |
|--------|-------|-----------|
| Core idea | Explicit control+data-flow extraction + capability policies | Task-specific rule induction + deterministic tool-call boundary enforcement |
| Model modification | None | None |
| Plan representation | Restricted Python code generated by P-LLM | Implicit (agent loop remains free-form) |
| Untrusted data handling | Q-LLM (no tools) + capability tracking | Content sanitizer + rule evaluator on every call |
| Policy style | Fine-grained capability checks (provenance + readers) | Whitelist / blacklist / ambiguous on tools, paths, network |
| Open-ended agents | Designed around a fixed plan; dynamic re-planning limited | Explicitly supports fully dynamic tool use at runtime |
| User interaction | Policy violations escalate; also used for ambiguous data | Ambiguous rule matches escalate; skill first-use inspection |
| Guarantees | Architectural (untrusted data cannot change control flow; policies enforce data-flow constraints) | Deterministic interception of tool calls outside the induced + baseline rule set |

CLAWGUARD paper explicitly notes that CaMeL is **incompatible with open-ended agents whose tool calls are determined dynamically at runtime**, which is one of the motivations for CLAWGUARD’s design.

## 8. Limitations (as stated or implied)

- Does not protect pure text-to-text attacks that never touch tools (phishing text shown only to the user, misleading summaries, etc.).
- “Data requires action” tasks (plan itself depends on untrusted content) cannot be solved without relaxing isolation or adding a second trusted planner instance.
- Current interpreter has no atomicity / rollback for partially executed side-effecting sequences.
- Utility can suffer when tool schemas are poorly documented or when the P-LLM fails to supply sufficient context to the Q-LLM.
- Security policies must be written (or at least curated); the paper’s evaluation uses hand-crafted policies for AgentDojo tools.
- Assumes the initial user prompt and any persistent memory are not already compromised.

---

## 9. Key Takeaways for Agents / Researchers

1. **By-design > by-training** for a large class of prompt-injection attacks: if untrusted data can never appear in the control-flow decision path, classic instruction-override injections become impossible.
2. **Data-flow hijacks remain dangerous** even after control-flow is locked; capability / information-flow control is needed to stop argument manipulation.
3. Explicit plans expressed as code give a natural place to attach provenance tracking and policy checks.
4. The Dual-LLM pattern is necessary but not sufficient; CaMeL is the first concrete, evaluated instantiation that also closes the data-flow channel.
5. Utility cost is modest for most suites once models are strong enough to use the Q-LLM effectively for schema discovery.
6. Residual risk shifts toward (a) attacks that only affect displayed text and (b) the quality / completeness of the security policies themselves.
