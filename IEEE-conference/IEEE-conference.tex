\begin{abstract}
  Tool-using agents built on large language models (LLMs) can be manipulated through instructions embedded in tool output or tool descriptions. As tools move into email, calendars, databases, and programming languages, this risk will continue to grow. Existing defenses modify the model itself, add a judge call after each agent action, or require a user to hand-author a policy for each tool. These methods do not scale well and do not provide complete protection. IntentGate is a lightweight middleware gate that extracts an intent contract directly from the user's trusted request before any malicious content is added. Each tool call is evaluated by its similarity to the extracted contract and a simple rule-based veto. Based on this evaluation, the call is allowed, blocked, or escalated to human review. This is done without requiring a direct LLM call for every action taken by the agent. The location of IntentGate provides a single point at which all tool calls occur, so the required policy comes from the user rather than from any content provided by an attacker. Evaluation was performed on two attack types: indirect injection on 2{,}108 InjecAgent cases and tool poisoning on 1{,}348 MCPTox cases. Under static attacks, attack success on InjecAgent falls from 19.0\% to 0.7\%, and attack-influenced MCPTox tool calls fall from 20.7\% to 10.7\%. Both benchmarks show large reductions. The gate adds 16--20 ms p95 CPU latency and needs no hand-authored per-tool contracts, compared with 145 for the ToolGate baseline. Additional testing on a second backbone (qwen3.5:4b) produced a comparable ASR reduction on InjecAgent (27.1\% to 2.1\%). The evaluation of benign utility, prompt baselines, and adaptive probes remains preliminary.
\end{abstract}

\section{Introduction}

LLM agents that use tools have access to the user's environment, including email, calendars, databases, and code, through a continuous cycle similar to ReAct~\cite{yao2023react}. At the same time, this access is also the attack surface. An attacker could send instructions via an email attachment, calendar invitation, database entry, or tool output, which are examples of indirect prompt injection~\cite{greshake2023notwhat,perez2022ignore}. A malicious tool description in the Model Context Protocol (MCP) could direct the agent through tool poisoning, described on actual MCP servers~\cite{wang2026mcptox,radosevich2025mcp}. In either case the agent acts on the attacker's instruction without user authorization, which is the excessive-agency risk in the OWASP Top 10 for LLM applications~\cite{owasp2025llmtop10}. Current defenses modify the model, make a judge call on the input, or require a hand-authored tool policy before execution, and a few derive the policy directly from the task~\cite{shi2025progent}. IntentGate is a middleware gate that evaluates each tool call against an intent contract extracted from the trusted user request. It is evaluated on InjecAgent for indirect injection and MCPTox for tool poisoning.

Some prior defense approaches differ in how and where control is enforced. Model-based defenses modify either the model itself or its training data. However, CaMeL modifies the model by placing it within a planning-execution architecture that includes capability tracking~\cite{debenedetti2025camel}. StruQ also alters the model through fine tuning it to differentiate the task-specific instruction from the relevant input data~\cite{chen2025struq}. Similarly, SecAlign uses preference optimization to achieve this same goal~\cite{chen2025secalign}. Models can be trained using an instruction hierarchy to force them to prioritize their most trusted instructions~\cite{wallace2024instruction}. The above-mentioned defense strategies all require model cooperation and have not been directly compared against each other for use against InjecAgent or MCPTox.

The open question is whether a gate that scores each tool call against a contract from a single trusted request can reduce attacks on both benchmark classes. On InjecAgent, attack success fell from 19.0\% to 0.7\%, and on MCPTox attack-influenced tool calls fell from 20.7\% to 10.7\%. The gate adds 16--20 ms p95 CPU latency and needs no hand-authored per-tool contracts.

\section{Background and Related Work}

\subsection{Threat model}
This threat model is a tool-using LLM agent in a ReAct-style loop~\cite{yao2023react}. Based upon a trusted user request, the agent proposes potential tool calls, then runs those calls, receives output, and continues running calls until there is a result provided to the user. The attacker may introduce malicious content either through tool descriptions (tool poisoning) or through retrieved or returned content (indirect injection). Additionally, tool-selection attacks allow the agent to select a registered attacker tool even when the user's task is benign~\cite{shi2025toolhijacker}. The attacker's goal is to make the agent execute an unauthorized tool call (data exfiltration, message sending, state changes, or credential exposure). The defender's goal is to block or escalate unauthorized tool calls without disrupting legitimate task completion. Everything following the initial request (tool definitions returned by a registry, tool outputs, injected document text) is potentially attacker-controlled. Attack content includes manually written text as well as optimized sequences~\cite{zou2023universal}, and earlier studies describe related failure modes in emulated agent environments~\cite{ruan2024identifying}.

\subsection{Defenses}
Model-level defenses track information flow at the model or runtime level. CaMeL~\cite{debenedetti2025camel} uses a planner-executor approach with capability-based taint tracking, so data from attacker-controlled sources cannot reach tool arguments. StruQ~\cite{chen2025struq} fine-tunes the model to separate instructions from data with structured queries, and SecAlign~\cite{chen2025secalign} applies preference optimization to the same end. Instruction-hierarchy training~\cite{wallace2024instruction} teaches the model to prioritize privileged instructions. All of these require model cooperation, and none has a head-to-head adversarial evaluation on InjecAgent or MCPTox. Data-level defenses mark or transform untrusted text. Spotlighting~\cite{hines2024defending} transforms retrieved content into clearly delimited forms. Guardrail toolkits such as NeMo Guardrails~\cite{rebedea2023nemo} enforce programmable rails around the model, but the model still makes the final call. Detection methods add training or inference cost: BIPIA fine-tunes a detector alongside its benchmark~\cite{yi2025benchmarking}, and MELON re-executes with masked tools and compares outputs~\cite{zhu2025melon}.

Judge-based defenses query a second language model to review each proposed call~\cite{taskshield2025}. They are flexible, but they add cost and latency with a language-model call on every action. They also create a new attack surface, because the judge can be prompt-injected, and produce implicit policies that are hard to audit. Contract-based defenses come closest to where this work enforces control. ToolGate~\cite{liu2026toolgate} enforces preconditions and postconditions for each tool at the tool-call boundary through hand-authored \emph{per-tool contracts}. In this reimplementation the policy source is the weakness. Coverage is incomplete (65/801 MCPTox tools, 8.1\% distinct and 37.2\% availability-weighted), and attacker-registered tools have no contract. Progent version 3~\cite{shi2025progent} derives its initial symbolic policy from the user's task and updates it during execution. A solver-based check (SMT) permits narrowing automatically and requires approval for expansion. Its call check is symbolic, while IntentGate freezes its contract and uses embedding scores plus vetoes. ClawGuard~\cite{clawguard2026} applies constraint specifications for tasks based on users' defined objectives. ClawGuard confirms all constraints via user interaction. ClawGuard has been applied to InjecAgent and MCPTox, so this work is not the first to derive policy from user input. Prompt Flow Integrity~\cite{kim2025promptflow} includes agent isolation and data tracking to prevent privilege escalations. TrustAgent~\cite{hua2024trustagent} utilizes a manually authored constitution, so its evaluation used emulation, not live tool execution. A recent design-pattern survey~\cite{beurerkellner2025design} concluded that secure agents prohibit unverified input from controlling sensitive operations.

AgentDojo~\cite{debenedetti2024agentdojo}, InjecAgent~\cite{zhan2024injecagent}, and Agent Security Bench~\cite{zhang2025asb} provided the framework for the injection-based test cases. Wang et al.~\cite{wang2026mcptox} developed MCPTox for tool poisoning. There is no mechanism for protecting against poisoned registrations (a weakness of the MCP)~\cite{anthropic2024mcp,radosevich2025mcp}. Zhan et al.~\cite{zhan2025adaptive} demonstrated that adaptive attackers can defeat statically designed defensive systems. As such, the primary focus is static attacks, and preliminary results for an adaptive attacker probing exercise were achieved offline.

\subsection{Research gap}
ToolGate requires a hand-authored contract for each tool~\cite{liu2026toolgate}. Progent creates a symbolic policy and modifies it in real time~\cite{shi2025progent}. ClawGuard generates constraint-based policies (task-scoped) based on the user's goal, then asks the user to verify~\cite{clawguard2026}. Task Shield implements a language-model judge on every action~\cite{taskshield2025}. IntentGate parses the trusted input request into a single, immutable contract and enforces that contract using a CPU-embedded scoring system and a deterministic veto mechanism. As such, IntentGate does not require a new model to be developed or retrained, nor does it implement a new LLM for each action or tool. The authors' measured contribution was comparing the results of their implementation of IntentGate against an implementation of ToolGate on two benchmarks: an injection benchmark and a small subset of a tool poisoning benchmark. Additionally, they measured the setup costs directly. Specifically, they created 145 total contracts as part of the ToolGate baseline and zero as part of their IntentGate implementation.

\section{Method}

\subsection{System overview and ordering invariant}
IntentGate sits between the agent and the executor. Figure~\ref{fig:gate} shows the pipeline. The ordering invariant is strictly enforced. The intent contract is parsed from the trusted user request \emph{before} tool definitions or any attacker content (injected observations, poisoned tool descriptions) are assembled. Tool outputs are never passed to the parser. Every proposed tool call, user-initiated and attacker-influenced alike, passes through \texttt{GateMiddleware.execute()} with no bypass path.

\subsection{Intent parser and contract schema}
A trusted intent parser (an LLM with temperature 0, JSON mode, one repair retry) reads the user request once per session and outputs an intent contract, the request-derived policy used by the gate.
\begin{equation}
  C = (A, K, H), \label{eq:contract}
\end{equation}
In this contract, $A$ is the set of allowed (entity, operation, resource) elements, $K$ is a set of numeric and path constraints, and $H$ is a set of high-risk flags. The implementation represents $A$ as the contract's goals, expected tool categories, and permitted data access, $K$ as argument constraints, and $H$ as side-effect limitations. If a call has contact with an element outside of $A$, violates a constraint within $K$, or contains a flag within $H$, then it will fail the rule check and trigger the veto. The schema is versioned and locked for the evaluation. The contract is embedded only once during each session and then reused. Only the proposed call is embedded at decision time. Therefore, the agent's prompt remains cacheable and the gate is removed from the prompt.

\subsection{Scorer}
Each proposed tool call $c$ is evaluated relative to the contract. The semantic component converts the cosine similarity between the contract embedding $e_C$ and the call embedding $e_c$ into $[0,1]$:
\begin{equation}
  S_{\mathrm{sem}} = \frac{1 + \cos(e_C, e_c)}{2} = \frac{1}{2}\left(1+\frac{e_C \cdot e_c}{\lVert e_C \rVert \, \lVert e_c \rVert}\right), \label{eq:sem}
\end{equation}
The rule component is also deterministic: $S_{\mathrm{rule}} \in \{0,1\}$. It is equal to 1 if the call satisfies all constraints in $K$ and 0 otherwise. The overall score is
\begin{equation}
  S = \alpha \, S_{\mathrm{sem}} + (1 - \alpha) \, S_{\mathrm{rule}}, \label{eq:score}
\end{equation}
A veto results in setting $S=0$ prior to thresholding. The default value is $\alpha=0.7$. Both $\tau=0.75$ and $\delta=0.1$ are fixed values based on a 50-call pilot before any benchmark was performed. This study reports the operating point and does not assert that either $\tau$ or $\delta$ is optimal or that either value would be transferred across splits.

\subsection{Gate middleware and escalate band}
The middleware makes a decision for each call based on Equation~\ref{eq:decision}:
\begin{equation}
  \mathrm{decision}(c) =
  \begin{cases}
    \text{\textsc{block}},    & S_{\mathrm{rule}}=0 \ \text{or}\ S < \tau-\delta,           \\
    \text{\textsc{escalate}}, & S_{\mathrm{rule}}=1 \ \text{and}\ \tau-\delta \le S < \tau, \\
    \text{\textsc{allow}},    & \text{otherwise},
  \end{cases} \label{eq:decision}
\end{equation}
The block case is fail-closed. The escalate case sends the call to human review and counts as a block in benchmark mode but is displayed to users in demo mode. Algorithm~\ref{alg:gate} shows the full procedure. Of the 583 escalated calls, 60.7\% targeted attacker tools, 14.8\% targeted user tools, and 24.5\% targeted other tools. No additional LLM calls are made per action by the gate. As such, measured p95 per-call latency is 16--20 ms on CPU.

\begin{algorithm}[t]
  \caption{Gate decision for one proposed tool call}
  \label{alg:gate}
  \footnotesize
  \begin{algorithmic}[1]
    \Require contract $C=(A,K,H)$ with embedding $e_C$; tool call $c$ with embedding $e_c$; parameters $\alpha,\tau,\delta$
    \Ensure decision $d$: allow, block, or escalate
    \State $S_{\mathrm{sem}} \gets \frac{1 + \cos(e_C, e_c)}{2}$
    \State $S_{\mathrm{rule}} \gets 1$ if $c$ satisfies $A$ and $K$, else $0$
    \State $S \gets \alpha S_{\mathrm{sem}} + (1-\alpha) S_{\mathrm{rule}}$
    \If{$S_{\mathrm{rule}}=0$ or $S < \tau-\delta$}
    \State $d \gets \mathrm{block}$ \Comment{fail-closed hard veto}
    \ElsIf{$S < \tau$}
    \State $d \gets \mathrm{escalate}$ \Comment{human-review band}
    \Else
    \State $d \gets \mathrm{allow}$
    \EndIf
    \State \Return $d$
  \end{algorithmic}
\end{algorithm}

\section{ToolGate Baseline (B2)}

The main baseline has been a minimal reimplementation of ToolGate~\cite{liu2026toolgate}: contracts with preconditions $P$ and post-conditions $Q$ on a symbolic state space, together with the ability to save snapshots and roll-back after a failed post-condition. Only the evaluated tool set has been covered by contracts. Of the user and attacker tools of InjecAgent (79/79), MCPTox registered tools (65/801) had 8.1\% distinct and 37.2\% availability-weighted. No silent allowance exists if no contracts exist: they have been accounted for as \texttt{no\_contract} and logged. Instead of executing a ToolBench run, fidelity has been reviewed using contract reviews and recorded-call replays.

Hand-authored contracts were required for ToolGate: 145 total, and none were needed for IntentGate, since the contract was automatically generated based upon the request. Expanding contracts towards 84.9\% weighted coverage on MCPTox did not result in reduced attack success, because an attack call will look like a normal query. The call itself is legitimate. However, the registration is poisoned. As such, the ToolGate results are statistically indistinguishable from the unprotected baseline results for MCPTox, thus supporting this comparison.

\section{Evaluation}

\subsection{Benchmarks and cases}
\textbf{InjecAgent}~\cite{zhan2024injecagent}: indirect prompt injection into tool-integrated agents, 2,108 cases (data-stealing and direct-harm attacker intents, base and enhanced settings). \textbf{MCPTox}~\cite{wang2026mcptox}: tool-poisoning attacks against real-world MCP servers, 1,348 static-snapshot cases. MCPTox results are scoped to the static snapshot. Live-server testing has been deferred.

\subsection{Metrics}
Attack success rate (ASR) represents the fraction of attack cases in which the attacker achieved their goal. For MCPTox, ASR represents the attack-influenced calls because the heuristic evaluator identifies evidence of payload or sensitive-path. The block rate is defined as the ratio of gated calls that are either blocked or escalated. Valid rate is the ratio of user-tool calls allowed by the gate, a call-level metric to represent an overall assessment of how useful the system is. Latency provides two metrics regarding overhead caused by gating: the 50th and 95th percentiles of all calls through each gate.

\subsection{Baselines and ablations}
B1 is the unprotected agent. B2 is the ToolGate reimplementation. IntentGate employs $\tau=0.75$, $\delta=0.1$, and $\alpha=0.7$. The full matrix includes three ablations: A1 semantic-only (rule veto disabled), A2 rule-only (embeddings disabled), and A3 raw-request embedding (similarity to the request text instead of the parsed contract). Each condition employed identical prompts, tool blocks, agent model (gpt-4o-mini), embedding model (all-MiniLM-L6-v2~\cite{reimers2019sentence}), and seed 42.

\subsection{Statistics}
Comparisons used the paired McNemar test with continuity correction~\cite{dietterich1998approximate}. Confidence intervals used a seeded bootstrap with 10k resamples for each benchmark and risk breakdown. The ten non-Other risk breakdowns use Bonferroni correction ($\alpha=0.005$). Post-hoc power is 1.0 at $\alpha=0.005$ for both benchmarks. Full-matrix results are presented as-is. Pilot results are labeled preliminary.

\section{Results}

\subsection{Main results}
Table~\ref{tab:headline} and Figure~\ref{fig:bars} summarize the headline result. On InjecAgent, IntentGate reduces ASR from 19.0\% to 0.7\%. On MCPTox, it reduces attack-influenced calls from 20.7\% to 10.7\%. On the primary slices (the enhanced data-stealing portion of InjecAgent and the full MCPTox snapshot), McNemar gives $p=1.3\mathrm{e}{-}33$ and $p=1.25\mathrm{e}{-}07$. The ToolGate baseline reduces ASR by 1.8 percentage points (17.2\% vs.\ 19.0\%) on InjecAgent and is not statistically distinguishable from the unprotected agent on MCPTox. Call-level utility is reported with the benign-task pilot in Section~\ref{sec:validation}.

\subsection{Setup cost}
IntentGate requires zero hand-authored contracts. ToolGate requires 145 total contracts and covers 79/79 InjecAgent and 65/801 MCPTox tools (full matrix). Extending the MCPTox set to 583 ToolGate contracts raised weighted coverage to 84.9\% without closing the gap. ToolGate's paper does not report this setup-cost metric.

\subsection{Ablations}
Semantic scoring alone reaches 0.0\% ASR on InjecAgent. The rule-only ablation (A2) is the weakest condition, with 14.7\% ASR on InjecAgent and 263 attack-influenced MCPTox calls, close to the unprotected agent on the hard slices. Semantic-only (A1) detects more than the full gate on MCPTox (81 vs.\ 144 attack-influenced calls) but over-blocks legitimate calls, as the benign-task pilot shows. The raw-request ablation (A3) matches the full gate on InjecAgent (0.7\% both) and catches slightly more attacks on MCPTox (116 vs.\ 144 attack-influenced calls). The contract's value is therefore utility and auditability. Headline ASR is similar. The false-escalate rate is 14.8\% over those 583 escalated calls.

\subsection{Error taxonomy}
Thirteen InjecAgent failures remain. All are read-only exfiltration calls with $S \in [0.75,0.79]$, just above $\tau$. All 13 were already allowed, and rewording them to sound like the user's request raised $S$ by 0.0112 on average without moving any additional case across $\tau$. These prose variants therefore do not change the operating point. The remaining MCPTox failures cluster in poisoned-registration cases whose calls look like legitimate queries, so no request-level rule fires.

\subsection{Validation results (preliminary)}
\label{sec:validation}
A second backbone, qwen3.5:4b, replicates the ASR reduction on InjecAgent (27.1\% $\rightarrow$ 2.1\%, $n=100$ per condition). gpt-6-luna is excluded because its prose-only output never participates in the ReAct-style loop. On 2,013 gated calls, the block rate is 42.4\% for specific contracts, 33.0\% for vague contracts, and 41.4\% overall.

The benign-task pilot (50 clean cases) compares the unprotected agent, the full gate, and the semantic-only ablation. User-tool allowed rates are 16.0\%, 12.0\%, and 8.0\%. Clean-call block rates are 0.0\%, 25.0\%, and 42.9\%. Semantic-only over-blocks legitimate calls, so the contract preserves more of them in this comparison.

The prompt-baseline pilot tests 50 attack cases per condition. ASR is 6.8\% with no defense prompt, 4.3\% with delimiters, 4.3\% with sandwiching, and 8.9\% with instructional prevention. DeepSeek V4.1 Flash refused the static injections (0/100 in both conditions), so its delta is undefined. This is a model-level refusal, not a gate effect. Phrasings that change how the injection is delivered stayed at or below 2.2\% gated ASR. All pilot numbers are preliminary.

\section{Limitations}

Static attacks were studied. There was no assertion to the effect that adaptive attackers would be able to perform better than the static attacker. An offline probe can create a copy of the user's request into free-text tool arguments and cause $S$ to exceed $\tau$. A single backbone (gpt-4o-mini) is used for all elements of the full matrix. qwen3.5:4b replicates the delta found in InjecAgent.

Contract coverage for MCPTox tools that are outside the subset evaluated in ToolGate remains low by design. Valid rate refers to the percent of the user's requests to use tools allowed by the system and not overall success of completing tasks. The MCPTox attack-influenced metric is obtained through a heuristic evaluator (payload and sensitive path evidence) and therefore is less detailed than an objective evaluator.

\section{Conclusion}

The results show that an action gate can derive its policy automatically from the user's request and enforce it with embedding similarity plus a deterministic veto at the tool-call chokepoint. The gate needs no hand-authored per-tool contracts, adds 16--20 ms p95 latency, and reduces attack success on an injection and a tool-poisoning benchmark. The reproducible artifact is released after acceptance. Future work covers adaptive-attacker hardening, live-server MCPTox evaluation, and multi-turn drift.
