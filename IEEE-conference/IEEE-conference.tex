\begin{abstract}
Tool-using agents built on large language models (LLMs) can be redirected by instructions hidden in tool output or tool descriptions, a risk that grows as agents reach email, calendars, databases, and code. Existing defenses modify the model, add a judge call per action, or require hand-authored per-tool policies, so enforcement stays costly or incomplete. This paper presents IntentGate, a lightweight middleware gate that derives an intent contract once from the user's trusted request, before any attacker content is loaded. Every proposed tool call is scored by embedding similarity to the contract plus a deterministic rule veto, then allowed, blocked, or escalated, with no LLM call per action. The design targets the chokepoint every tool call crosses, and its policy comes from the user, not from text an attacker can touch. The two benchmarks cover the two attack classes in scope: InjecAgent for indirect injection and MCPTox for tool poisoning. On InjecAgent, attack success falls from 19.0\% to 0.7\%. On MCPTox, attack-influenced tool calls fall from 20.7\% to 10.7\%. The gate adds 16--20 ms p95 CPU latency and requires zero setup, compared with 145 hand-authored baseline contracts. Pilots on additional backbones, benign-task blocking, prompt baselines, and adaptive delivery are reported as preliminary.
\end{abstract}

\section{Introduction}

Tool-using LLM agents act through mail, calendars, databases, and code in a ReAct-style loop~\cite{yao2023react}. That reach is also the attack surface. Instructions hidden in retrieved documents or tool output can redirect the agent through indirect prompt injection~\cite{greshake2023notwhat,perez2022ignore}. A malicious tool description can redirect it through tool poisoning, documented on real servers of the Model Context Protocol (MCP)~\cite{wang2026mcptox,radosevich2025mcp}. In both cases the agent performs actions the user never authorized, which is the excessive-agency risk in the OWASP Top 10 for LLM applications~\cite{owasp2025llmtop10}. Recent surveys list more than thirty attack techniques across agent workflows and protocol layers~\cite{ferrag2026survey}. Existing defenses include model-level changes, judge calls, manual contracts, and automatically derived task policies~\cite{shi2025progent}. This study tests a frozen request contract with CPU embedding scores and deterministic vetoes at the tool boundary. This paper introduces IntentGate: a middleware gate that scores every proposed tool call against an intent contract parsed once from the trusted user request, before any attacker content is loaded. The evaluation covers an injection benchmark (InjecAgent) and a tool-poisoning benchmark (MCPTox).

Prior defenses differ in where they enforce control. Model-level methods change the model or its training data. CaMeL~\cite{debenedetti2025camel} wraps the model in a planner-executor design with capability tracking. StruQ~\cite{chen2025struq} and SecAlign~\cite{chen2025secalign} fine-tune the model to separate instructions from data, and instruction-hierarchy training~\cite{wallace2024instruction} teaches models to prioritize trusted instructions. These approaches need model cooperation and report no head-to-head evaluation on InjecAgent or MCPTox. Data-level methods mark or filter untrusted text. Spotlighting~\cite{hines2024defending} transforms it. Guardrail toolkits~\cite{rebedea2023nemo} enforce programmable rails, but the model still makes the final call.

The empirical question is whether a score gate built from a frozen request contract reduces attacks on both benchmark classes under a shared comparison protocol. IntentGate derives the contract automatically from the user request and scores each call by embedding similarity plus a deterministic veto. It then decides allow, block, or escalate at the call boundary, with no LLM call per action. On the full evaluation, attack success on InjecAgent falls from 19.0\% to 0.7\%, and attack-influenced MCPTox calls fall from 20.7\% to 10.7\%. The gate adds 16--20 ms p95 CPU latency and requires no manual per-tool contracts. A ToolGate reimplementation with 145 contracts stays statistically indistinguishable from the unprotected agent.

\section{Background and Related Work}

\subsection{Threat model}
The threat model is a tool-using LLM agent in a ReAct-style loop~\cite{yao2023react}. Given a trusted user request, the agent proposes tool calls, executes them, observes the results, and repeats until it produces a final answer. Attacker content arrives through tool descriptions (tool poisoning) or through retrieved or returned content (indirect injection). Tool-selection attacks can also make the agent choose an attacker-registered tool even when the user's task is benign~\cite{shi2025toolhijacker}. The attacker's goal is to cause the agent to execute a tool call the user did not authorize: data exfiltration, message forwarding, state mutation, or credential access. The defender's goal is to block or escalate such calls while preserving legitimate task completion. The initial user request is assumed trustworthy. Everything after it (tool definitions returned by a registry, tool outputs, injected document text) is potentially attacker-controlled. Attack content ranges from manually written text to optimized adversarial sequences~\cite{zou2023universal}, and earlier risk studies describe related failure modes in emulated agent environments~\cite{ruan2024identifying}.

\subsection{Defenses}
Model-level defenses track information flow at the model or runtime level. CaMeL~\cite{debenedetti2025camel} wraps the model in a planner-executor design with capability-based taint tracking, so data from attacker-controlled sources cannot reach tool arguments. StruQ~\cite{chen2025struq} fine-tunes the model to separate instructions from data with structured queries, and SecAlign~\cite{chen2025secalign} applies preference optimization to the same end. Instruction-hierarchy training~\cite{wallace2024instruction} teaches the model to prioritize privileged instructions. All of these require model cooperation and publish no head-to-head adversarial evaluation on InjecAgent or MCPTox. Data-level defenses mark or transform untrusted text. Spotlighting~\cite{hines2024defending} converts retrieved content into clearly delimited forms. Guardrail toolkits such as NeMo Guardrails~\cite{rebedea2023nemo} enforce programmable rails around the model, but the model still makes the final call. Detection methods add training or inference cost: BIPIA fine-tunes a detector alongside its benchmark~\cite{yi2025benchmarking}, and MELON re-executes with masked tools and compares outputs~\cite{zhu2025melon}.

Judge-based defenses ask a second language model to vet each proposed call~\cite{taskshield2025}. They are flexible, but they add a language-model call on every action, which adds cost and latency. They also introduce a new attack surface, because the judge can be prompt-injected, and produce implicit policies that are hard to audit. Contract-based defenses come closest to where this work enforces control. ToolGate~\cite{liu2026toolgate} enforces hand-authored contracts with preconditions and postconditions for each tool at the tool-call boundary, the same chokepoint used here. Its weakness is the policy source. Contracts are written manually per tool, coverage is incomplete (65/801 MCPTox tools, 8.1\% distinct and 37.2\% availability-weighted), and attacker-registered tools have no contract. Progent version 3~\cite{shi2025progent} derives its initial symbolic policy from the user's task and updates it during execution. A solver-based check (SMT) permits narrowing automatically and requires approval for expansion. Its call check is symbolic, while IntentGate freezes its contract and uses embedding scores plus vetoes. ClawGuard~\cite{clawguard2026} derives task-specific constraints from the user's stated objective and enforces them deterministically, with a user confirmation step. It reports results on six injection benchmarks including InjecAgent and MCPTox, so this paper does not claim to be the first to derive policy from the request. Prompt Flow Integrity~\cite{kim2025promptflow} prevents privilege escalation through agent isolation and data tracking, and it is evaluated on AgentDojo and AgentBench. TrustAgent~\cite{hua2024trustagent} uses a hand-authored constitution and is evaluated by emulation, not live tool execution. A recent design-pattern survey~\cite{beurerkellner2025design} argues that the safest agent designs never let untrusted data steer privileged actions, which supports the gate placement used in this paper.

AgentDojo~\cite{debenedetti2024agentdojo}, InjecAgent~\cite{zhan2024injecagent}, and Agent Security Bench~\cite{zhang2025asb} provide the injection benchmarks. MCPTox~\cite{wang2026mcptox} provides the tool-poisoning benchmark, and the MCP specification itself ships no defense against poisoned registrations~\cite{anthropic2024mcp,radosevich2025mcp}. Zhan et al.~\cite{zhan2025adaptive} show that adaptive attackers break defenses that look strong under static attacks. This paper therefore scopes its primary claims to static attacks and reports an offline adaptive-attacker probe as preliminary.

\subsection{Research gap}
The closest systems differ from IntentGate in policy source and enforcement. ToolGate needs a hand-authored contract for every tool. Progent derives a symbolic policy and updates it during execution. ClawGuard derives task-scoped constraints from the user objective and asks the user to confirm them. Task Shield adds a language-model judge on every action. IntentGate instead parses the trusted request once into a frozen contract and enforces it with a CPU embedding score plus a deterministic veto. It needs no model change, no retraining, no per-action LLM, and no per-tool authoring. The measured contribution is a head-to-head comparison with a ToolGate reimplementation on both an injection benchmark and a tool-poisoning benchmark, with setup cost measured directly (0 vs.\ 145 contracts).

\section{Method}

\subsection{System overview and ordering invariant}
IntentGate sits between the agent and the executor. Figure~\ref{fig:gate} shows the pipeline. The ordering invariant is strict. The intent contract is parsed from the trusted user request \emph{before} tool definitions or any attacker content (injected observations, poisoned tool descriptions) are assembled. Tool outputs are never passed to the parser. Every proposed tool call, user-initiated and attacker-influenced alike, passes through \texttt{GateMiddleware.execute()} with no bypass path.

\subsection{Intent parser and contract schema}
A trusted intent parser (an LLM at temperature 0, JSON mode, one repair retry) reads the user request once per session and emits an intent contract
\begin{equation}
C = (A, K, H), \label{eq:contract}
\end{equation}
In this contract, $A$ is the set of allowed (entity, operation, resource) elements, $K$ is a set of numeric and path constraints, and $H$ is a set of high-risk flags. A call that touches an element outside $A$, violates a constraint in $K$, or matches a flag in $H$ fails the rule check and triggers the veto. In the implementation these map to the contract's goals and expected tool categories ($A$), side-effect limits ($K$), and fail-closed high-risk defaults ($H$). The schema is versioned and frozen for the evaluation. The contract is embedded once per session and reused. Only the proposed call is embedded at decision time, which keeps the agent prompt cacheable and the gate out of the prompt.

\subsection{Scorer}
Each proposed tool call $c$ is scored against the contract. The semantic component is the cosine similarity between the contract embedding $e_C$ and the call embedding $e_c$:
\begin{equation}
S_{\mathrm{sem}} = \frac{1+\cos(e_C, e_c)}{2} = \frac{1}{2}\left(1+\frac{e_C \cdot e_c}{\lVert e_C \rVert \, \lVert e_c \rVert}\right), \label{eq:sem}
\end{equation}
The rule component is deterministic: $S_{\mathrm{rule}} \in \{0,1\}$. It is 1 when $c$ passes all constraints in $K$ and 0 when the veto fires. The combined score is
\begin{equation}
S = \alpha \, S_{\mathrm{sem}} + (1 - \alpha) \, S_{\mathrm{rule}}, \label{eq:score}
\end{equation}
The default is $\alpha = 0.7$. The threshold $\tau = 0.75$ and half-width $\delta = 0.1$ were fixed on a 50-call pilot before any benchmark run. This paper reports the operating point and does not claim that the choice is optimal or that it transfers across splits.

\subsection{Gate middleware and escalate band}
The middleware decides per call:
\begin{equation}
\mathrm{decision}(c) =
\begin{cases}
\text{\textsc{block}}, & S_{\mathrm{rule}}=0 \ \text{or}\ S < \tau-\delta, \\
\text{\textsc{escalate}}, & S_{\mathrm{rule}}=1 \ \text{and}\ \tau-\delta \le S < \tau, \\
\text{\textsc{allow}}, & \text{otherwise},
\end{cases} \label{eq:decision}
\end{equation}
The block case is fail-closed. The escalate case routes to human review, is counted as a block in benchmark mode, and is shown to the user in demo mode. Algorithm~\ref{alg:gate} lists the full procedure. Of escalated calls, 60.7\% target attacker tools, 14.8\% target user tools, and 24.5\% target other tools (n=583 escalated calls, E21). The gate adds no LLM call per action. Measured p95 per-call latency is 16--20 ms on CPU.

\begin{algorithm}[t]
\caption{Gate decision for one proposed tool call}
\label{alg:gate}
\footnotesize
\begin{algorithmic}[1]
\Require contract $C=(A,K,H)$ with embedding $e_C$; tool call $c$ with embedding $e_c$; parameters $\alpha,\tau,\delta$
\Ensure decision $d$: allow, block, or escalate
\State $S_{\mathrm{sem}} \gets \frac{1+\cos(e_C, e_c)}{2}$
\State $S_{\mathrm{rule}} \gets 1$ if $c$ satisfies $A$ and $K$, else $0$
\State $S \gets \alpha S_{\mathrm{sem}} + (1-\alpha) S_{\mathrm{rule}}$
\If{$S_{\mathrm{rule}}=0$ or $S < \tau-\delta$}
  \State $d \gets \mathrm{block}$ \Comment{fail-closed hard veto}
\ElsIf{$S < \tau$}
  \State $d \gets \mathrm{escalate}$ \Comment{human-review band}
\Else
  \State $d \gets \mathrm{allow}$
\EndIf
\State \Return $d$
\end{algorithmic}
\end{algorithm}

\section{ToolGate Baseline (B2)}

The primary baseline is a minimal reimplementation of ToolGate~\cite{liu2026toolgate}: contracts with preconditions $P$ and postconditions $Q$ over a symbolic world state, plus snapshot and rollback when a postcondition fails. Contracts cover the evaluated tool subset only: InjecAgent 79/79 user and attacker tools (100\%), MCPTox 65/801 registered tools (8.1\% distinct and 37.2\% availability-weighted). Missing contracts are never silently allowed: they are counted as \texttt{no\_contract} and reported. Fidelity was validated by contract review and recorded-call replay instead of a ToolBench run.

Setup cost is measured directly: ToolGate requires 145 hand-authored contracts on InjecAgent, compared with zero setup for IntentGate, whose contract is derived from the request. On MCPTox, extending contracts toward 84.9\% weighted coverage leaves attack success flat, because attack calls look like legitimate queries. The attack is in the poisoned registration, so the tool call itself looks legitimate. ToolGate is statistically indistinguishable from the unprotected baseline on MCPTox, which supports the head-to-head comparison.

\section{Evaluation}

\subsection{Benchmarks and cases}
\textbf{InjecAgent}~\cite{zhan2024injecagent}: indirect prompt injection in tool-integrated agents, 2,108 cases (direct-harm and data-stealing attacker intents, in base and enhanced settings), frozen at pinned commits. \textbf{MCPTox}~\cite{wang2026mcptox}: tool poisoning on real-world MCP servers, 1,348 static-snapshot cases. MCPTox results are explicitly scoped to the static snapshot (live-server evaluation is deferred, and the poisoning-at-registration logic is identical in both).

\subsection{Metrics}
Attack success rate (ASR): share of attack cases where the attacker's objective is achieved. For MCPTox, the same quantity is reported as attack-influenced calls because the heuristic evaluator flags payload or sensitive-path evidence rather than a strict objective. Block rate: share of gated calls blocked or escalated, over all gated calls (12.4\% of 2{,}013). Intervention rate: share of user-tool calls blocked or escalated (31.0\% of 281 user-tool calls on InjecAgent). Valid rate: share of agent outputs that are valid, not a permission rate. Latency: p50/p95 per-call gate overhead. Setup cost: hand-authored contracts required.

\subsection{Baselines and ablations}
B1 is the unprotected agent. B2 is the ToolGate reimplementation. Ours is IntentGate at $\tau=0.75$, $\delta=0.1$, $\alpha=0.7$. The full matrix adds three ablations: A1 semantic-only (no rule veto), A2 rule-only (no embeddings), A3 raw-request embedding (similarity to the request text instead of the parsed contract). All conditions run with identical prompts, tool blocks, agent model (gpt-4o-mini), embedding model (all-MiniLM-L6-v2~\cite{reimers2019sentence}), and seed 42.

\subsection{Statistics}
All comparisons use the paired McNemar test with continuity correction~\cite{dietterich1998approximate}. Confidence intervals come from a seeded bootstrap with 10k resamples for each benchmark and risk breakdown. The 10 risk breakdowns use Bonferroni correction ($\alpha=0.005$). Post-hoc power is 1.0 at $\alpha=0.005$ for both benchmarks. Results from the full matrix are reported as-is. Pilot results are labeled preliminary.

\section{Results}

\subsection{Main results}
Table~\ref{tab:headline} and Figure~\ref{fig:bars} summarize the headline result. On InjecAgent, IntentGate reduces ASR from 19.0\% to 0.7\%. On MCPTox, it reduces attack-influenced calls from 20.7\% to 10.7\%. On the primary slices (the enhanced data-stealing portion of InjecAgent and the full MCPTox snapshot), McNemar gives $p=1.3\mathrm{e}{-}33$ and $p=1.25\mathrm{e}{-}07$. The ToolGate baseline reduces ASR by 1.8 percentage points (17.2\% vs.\ 19.0\%) on InjecAgent and is not statistically distinguishable from the unprotected agent on MCPTox. Call-level intervention counts appear with the ablations.

\subsection{Setup cost}
IntentGate requires zero hand-authored contracts. ToolGate requires 145 on InjecAgent and 65 on MCPTox (full matrix), extendable to 583 without closing the gap. ToolGate's paper does not report this setup-cost metric.

\subsection{Ablations}
Semantic scoring alone reaches 0.0\% ASR on InjecAgent, so the full gate is not the safest condition here. The rule-only ablation (A2) is the weakest, with 14.7\% ASR on InjecAgent and 263 attack-influenced MCPTox calls, close to the unprotected agent. Semantic-only (A1) also detects more on MCPTox (81 vs.\ 144 attack-influenced calls), and the raw-request ablation (A3) matches the full gate on InjecAgent (0.7\% both) while catching slightly more on MCPTox (116). Because the arms propose different calls, this comparison confounds the components. Replaying 2{,}013 identical frozen proposals (E31) separates them: the full gate's vetoes prevent 28 calls that semantic-only would allow, while semantic-only would allow 14 attacker-tool and 296 unknown-role calls that the full gate prevents. The contract's measured effect is a lower intervention rate on legitimate calls (87 of 281 user-tool calls blocked or escalated, 31.0\%, against 102 of 279, 36.6\%, for semantic-only) plus auditability and zero per-tool authoring. On identical proposals the gap is 71 of 199 versus 79 of 199, and it is a score band: a rule-passing call is allowed once $S_{\mathrm{sem}}\ge0.64$, so semantic-only blocks a band the full gate admits. Neither component dominates.

\subsection{Error taxonomy}
Thirteen InjecAgent failures remain: all are read-only exfiltration calls with $S\in[0.75,0.79]$, just above $\tau$. Rewriting these calls to sound like the user's request inflates $S$ by only +0.0112 on average, with 0/13 cases newly crossing $\tau$, so these prose variants do not move the threshold. The remaining MCPTox failures cluster in poisoned-registration classes no contract covers.

\subsection{Validation results (preliminary)}
\label{sec:validation}
A second backbone, qwen3.5:4b, reproduces the reduction at pilot scale (27.1\% $\rightarrow$ 2.1\%, n=100 attack cases per condition, E18). gpt-6-luna is excluded because it produced invalid, non-tool-calling outputs in 40--80\% of its 20 cases per condition. On 2,013 gated calls the block-or-escalate rate is 12.8\% for specific contracts, 9.6\% for vague contracts, and 12.4\% overall. A call-level benign pilot (50 cases per arm) compares three conditions. Only 8, 8, and 7 of those cases produced any tool call: the user tool was allowed in 8, 6, and 4 of 50 cases, and 0, 2, and 3 of 8, 8, and 7 proposed calls were blocked. These counts cannot establish a utility difference; no end-to-end benign completion was measured. The prompt-baseline pilot tests 50 attack cases per condition. ASR is 6.8\% with no defense prompt, 4.3\% with delimiters, 4.3\% with sandwiching, and 8.9\% with instructional prevention. DeepSeek V4.1 Flash refused the static injections (0/100 in both conditions), so the third-backbone delta is undefined. This is a model-level refusal, not a gate effect. The benchmark cannot show a gate effect on that backbone. Phrasings that change how the injection is delivered stayed at or below 2.2\% gated ASR. All pilot numbers are preliminary.

\section{Limitations}

The primary claims are scoped to static attacks. Adaptive-attacker performance is not claimed. An offline probe that copies the user request into free-text tool arguments can inflate $S$ above $\tau$. In an offline replay, a six-token verbatim-echo guard blocks all 34 measured adaptive calls (11/11 call templates) with no new blocks among 194 allowed user-tool calls. The main results remain unchanged. MCPTox results are on a static snapshot, not live servers. The full matrix uses a single backbone (gpt-4o-mini). qwen3.5:4b reproduces the delta at pilot scale, and gpt-6-luna produced invalid, non-tool-calling outputs. DeepSeek's refusal is a model boundary, not evidence of gate generality. The parser is an LLM call once per session, included in the cost. Per-action enforcement uses no LLM.

Contract coverage for MCPTox tools outside the evaluated subset remains low by design (missing contracts are counted as \texttt{no\_contract} and never silently allowed). The valid rate measures valid agent outputs, not permission to act and not end-to-end task success. The benign pilot is call-level over 7--8 calls per arm and establishes no utility difference. Block and escalate are counted together, so no rate reported here is a pure false-positive rate. The MCPTox attack-influenced metric comes from a heuristic evaluator (payload and sensitive-path evidence), which is coarser than a strict objective check.

\section{Conclusion}

This paper shows that an action gate can derive its policy automatically from the user's request and enforce it with embedding similarity plus a deterministic veto at the tool-call chokepoint. The gate operates with zero setup cost, 16--20 ms p95 latency, and a measured reduction in attack success on both an injection and a tool-poisoning benchmark. The reproducible artifact is released after acceptance. Future work covers adaptive-attacker hardening, live-server MCPTox evaluation, and multi-turn drift.
